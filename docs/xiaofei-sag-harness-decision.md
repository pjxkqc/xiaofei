# SAG 与 Xiaofei Harness 的 P0 决策

## 决策

截至 2026-08-05，Xiaofei P0 继续交付现有 Harness，**暂不把 SAG 直接接入产品运行时**。
这是一项有复审条件的阶段性决定，不是永久否定 SAG。SAG 以及更轻量的知识治理方案只在
独立研究轨道中比较；在通过本文的安全、治理、复杂度、成本和效果门槛前，不进入 Xiaofei
的租户数据路径、知识发布路径、会话编排或客户可见发送路径。

本决定不改变当前 P0。当前行为与硬性不变量仍以
[`xiaofei-foundation.md`](./xiaofei-foundation.md)、
[`xiaofei-p0-framework.md`](./xiaofei-p0-framework.md) 和各实现边界 README 为准。
知识治理的在途工作也必须在自己的 Issue 和 PR 中独立审查；本文不把未合并方案描述成
已经上线的能力。

## 为什么现在继续 Harness

Harness 已经把“生成内容”和“授权执行”分开：租户边界、知识准入、会话所有权、
Guardrail、人工接管、Eval、Trace 与发送授权属于 Xiaofei 控制面，而模型与外部框架只能
提供受约束的候选结果。这个边界直接保护 `ownerEpoch`、租户隔离和客户可见发送，不能因
引入一个前台能力更完整的平台而隐式迁移。

直接接入 SAG 目前没有已记录的、可复现证据证明它能在不复制控制面的前提下改善 P0；
相反，它会立即引入双重知识状态、双重编排或双重权限来源的风险。先保持 Harness 单一
权威，再隔离验证最小能力，能让后续采用由数据决定，而不是由功能清单决定。

## SAG 前台能力的研究边界

这里的 “SAG 能力” 是待验证的候选能力集合，不是对某一版本的生产保证。研究必须先固定
产品、版本、部署模式和许可条款，再逐项用公开文档或可重复实验确认：

- 知识源导入、切分、索引、检索和来源展示；
- Agent、提示词、工具或工作流的可视化配置；
- 对话调试、测试集运行、结果比较和运营观察；
- 模型、检索器、工具和外部系统的适配入口；
- 面向运营人员的发布、回滚、审计或监控界面。

即使其中一项得到验证，SAG 也只能作为可替换的前台或适配器候选，不能据此取得 Xiaofei
的租户、知识版本、会话所有权、Guardrail 或发送授权。

## 责任边界

| 责任            | SAG 在研究中可提供的候选作用            | Harness 保留的权威责任                                            | 不可跨越的边界                                                 |
| --------------- | --------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------- |
| 租户隔离        | 展示或处理已脱敏、实验专用的租户标识    | 认证、Organization/Workspace 解析、数据访问授权与隔离测试         | SAG 的 workspace、project 或 API key 不能替代 Xiaofei 租户授权 |
| KU/CA 版本      | 辅助抽取、检索、草拟或比较候选内容      | KU Revision、CA Version、Test/Active 状态、准入、回滚与审计链     | SAG 索引或发布状态不能成为 Active 的事实来源                   |
| 上下文与记忆    | 提供临时、无权威的候选上下文            | `ConversationState`、持久化消息、租户范围、保留和删除规则         | 不把未审查的 SAG memory 回写为产品状态                         |
| 编排            | 在适配器内执行有界检索或候选生成        | LangGraph 会话状态机、Mastra 治理与生成边界、失败策略             | SAG 不能绕过统一入口或并行推进权威会话状态                     |
| Owner/Guardrail | 返回解释或风险信号                      | Owner、`ownerEpoch`、租约复核、最终 Guardrail 和 fail-closed 决策 | SAG 输出永远不是客户可见授权                                   |
| 人工接管        | 提供摘要或建议                          | 接管触发、`HandoffPackage`、所有权迁移与恢复                      | SAG 不直接改变 Owner，也不替人工操作员发送                     |
| Eval            | 运行候选检索或回答实验                  | 固定数据集、同版本准入断言、风险/缺知识用例与发布门禁             | SAG 自有评分不能替代 Harness Eval                              |
| Trace           | 暴露候选步骤或供应商日志                | 业务 Trace、决策因果、租户范围、审计保留和敏感信息控制            | 外部日志不是权威审计记录，且不得包含凭据或生产数据             |
| 渠道与发送授权  | 最多生成 `ReplyIntent` 候选或适配器结果 | 渠道绑定、幂等、Outbox、最终 Owner/Guardrail 复核与发送时 fencing | SAG 不持有渠道发送凭据，不调用客户可见发送接口                 |

任何未来集成都应优先是单向、可移除的适配器：Harness 提供最小、已授权的输入，SAG 返回
候选检索或候选文本，Harness 再独立完成准入、Guardrail、Owner 和发送复核。

## 直接接入的权衡

潜在收益包括更快验证知识摄取与检索界面、减少自建运营前台、复用现成适配器，以及缩短
候选能力的试验周期。但直接接入也会带来以下当前不可接受的成本：

- 两套租户、知识版本、会话或发布状态难以证明一致；
- 框架编排与现有 LangGraph/Mastra/领域内核产生重复权威；
- 外部 memory、Trace 和索引扩大数据驻留、删除、脱敏与审计范围；
- 模型候选、工具调用或渠道插件可能绕过 Owner/Guardrail/发送门禁；
- 新服务的升级、可用性、许可、可观测性和退出迁移形成持续运维成本；
- 为迁就平台对象模型而改写 Xiaofei 合同，会提高锁定和回滚难度。

因此，“功能存在”不是接入理由。只有一个可替换的最小适配器在受控实验中产生可量化净
收益，并保持 Harness 单一权威，才值得提出后续采用。

## 独立轻量研究轨道

研究是单独的治理工作，不是本 P0 PR 的隐藏实现。开始实验前必须创建独立 Issue，指定
单一 Owner、固定候选版本、数据分类、实验期限和销毁日期。研究遵守以下隔离规则：

1. 只使用合成或明确批准且脱敏的数据；禁止生产数据、凭据、Cookie、连接串和渠道密钥。
2. 使用独立环境、存储、账号和日志；不连接 Xiaofei Preview、UAT 或 Production 数据库。
3. 不修改 Harness runtime、schema、API、UI、CI，也不修改其他在途 Issue、分支或 PR。
4. 通过离线 fixture 和固定 Eval 集比较 SAG、当前 Harness，以及至少一个更轻的候选（例如
   无状态检索适配器或托管检索 API）。
5. 研究产物只包含脱敏指标、版本、配置摘要和删除证明；实验结束即销毁临时数据与资源。
6. 任一候选若要求取得 Owner、Guardrail 或发送权，直接淘汰，不进入性能权衡。

### 度量与门槛

开始前冻结数据集、问题集、当前 Harness 基线和计算口径；不得在看到结果后修改通过线。

| 维度   | 必须记录                                              | 进入采用评审的门槛                                                                                                            |
| ------ | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 治理   | 来源覆盖、版本可复现、删除/回滚、审计字段完整率       | 每个回答 100% 可追溯到固定候选版本和来源；重复运行可复现；删除与回滚演练全部通过                                              |
| 安全   | 跨租户探测、提示注入、越权工具、日志泄漏、发送绕过    | 零跨租户读取、零越权工具执行、零敏感信息泄漏、零绕过 Harness 发送门禁；任一失败即淘汰                                         |
| 效果   | 固定集检索命中、grounded 回答、错误准入、运营处理时间 | 相对 Harness 至少一项主要指标改善 10%，其他安全/质量指标不得退化；或运营处理时间降低至少 30%                                  |
| 性能   | 端到端 p50/p95、超时率和失败恢复                      | p95 相对 Harness 增幅不超过 20%，且故障能 fail closed 并回退到 Harness                                                        |
| 复杂度 | PoC 工期、产品边界数、长期服务数、升级与退出步骤      | PoC 不超过 5 个工程日；采用估算不超过 10 个工程日、2 个实现边界和 1 个新增长期服务；可在 1 个工程日内关闭适配器并回到 Harness |
| 成本   | 固定月费、每千次会话的模型/检索/存储/出网成本         | 总可变成本不高于 Harness 基线的 120%，且无未获批准的长期最低消费或不可逆许可约束                                              |

效果门槛是收益条件；治理、安全、复杂度和成本是硬门槛，不能用更高回答分数抵消。若实验
规模不足以支持一个阈值，应记录“证据不足”，而不是判定通过。

## 退出条件与未来采用门禁

研究在以下任一条件出现时结束并保持 Harness：硬门槛失败；候选没有达到净效果收益；
需要复制权威状态或发送能力；无法证明隔离、删除或退出；达到时间/成本预算仍证据不足。
结束时记录结果并销毁实验资源，不留下运行时 TODO 或半接入依赖。

只有全部门槛通过，才可以另开采用 Issue。该 Issue 必须重新审查威胁模型、数据处理、许可
与退出方案，定义适配器合同和唯一 Owner，拆分跨边界实现，并从当时接受的 `uat` 基线走
Draft PR、exact-head Quality/Preview 和人工合并流程。采用评审仍可选择“不接入”；研究
通过只代表值得评审，不代表已经获得上线或 Production 授权。
