# Xiaofei P0：SAG 与 Harness 的知识治理决策

## 决策

在 Xiaofei P0 阶段，**不把 SAG 直接接入为知识治理或运行时的主系统**。当前
`xiaofei-harness` 计划继续执行，并先以已定义的 KU/CA、受控对话和人工验收闭环证明
治理效果。

这不是对 SAG 的永久否决。SAG 或同类方案可以在与主线隔离的研究轨道中评估；只有通过
本文定义的采纳门槛，并获得单独的人工授权，才可提出后续集成 Feature。

本文中的“SAG”指本次评估的外部知识治理方案类别，而不是 Xiaofei 已依赖或已部署的
组件。本文不引入其实现、数据、凭据或运行时。

## 背景与问题

知识治理不止是把资料解析、索引并检索出来。Xiaofei 的客户可见回复还必须满足租户
边界、版本固定、对话状态、人工接管、最终 Guardrail 和发送授权等条件。当前 P0 已将
这些约束放在 vendor-neutral 的 `@repo/xiaofei` 内核和 Harness 编排边界，而不是交给
某个检索或知识产品。

SAG 这类方案可能让资料接入、知识结构化、检索证据和知识维护更成熟；但它只覆盖该链路
的前段。若在 P0 直接接入，仍须由 Xiaofei 保留后段的上下文、记忆、授权和渠道编排，
并额外解决两套状态、版本和审计证据之间的映射。因此当前的主要风险不在“能否检索”，
而在控制面变成两套真相源。

## 责任边界

| 能力                   | 当前 Harness / Xiaofei 的权威边界                    | SAG 或同类方案可研究的价值       | P0 决定                  |
| ---------------------- | ---------------------------------------------------- | -------------------------------- | ------------------------ |
| 资料接入、解析和归档   | 受租户边界约束的来源、KU Revision 与证据             | 改善结构化、治理工作流或检索索引 | 可研究，不替换当前事实源 |
| 检索和候选上下文       | 只从已发布、已审核、已固定版本的知识中选择           | 提供检索、重排或引用候选         | 仅能作为受控适配器候选   |
| KU/CA 版本与发布       | KU/CA、审核、Eval、Active/Test 状态                  | 无                               | 仍由 Xiaofei 管理        |
| 会话上下文与记忆       | `ConversationState`、持久状态、Trace 与 `ownerEpoch` | 可能提供辅助记忆能力             | 不引入第二个会话真相源   |
| 编排与模型调用         | LangGraph 编排、Mastra 候选生成、领域准入            | 无                               | 仍由 Harness 管理        |
| 风险、所有权和人工接管 | Owner、Lease、Handoff、最终 Guardrail                | 无                               | 仍由 Xiaofei 内核管理    |
| 客户可见发送与渠道     | 最终授权、Outbox/渠道适配和审计                      | 无                               | 不向外部知识系统委托     |

这一区分保留了一个硬边界：外部知识能力即使给出候选上下文，也不能发布知识版本、改变
会话所有权、绕过 Guardrail，或直接发送客户回复。

## 为什么当前不直接接入 SAG

1. **覆盖范围不完整。** SAG 解决资料治理与检索的前段，不解决 Xiaofei 已经必须承担的
   租户授权、KU/CA 发布、长对话状态、Owner Lease、人工接管、Eval、Trace、渠道和发送
   授权。直接接入不会移除 Harness，而是让 Harness 多一个需要治理的依赖。
2. **上下文与记忆会增加集成复杂度。** 若 SAG 与 Xiaofei 都保存或推导会话/记忆，必须
   明确版本、失效、回放、删除、租户隔离和故障恢复的唯一真相源。P0 目前没有必要为
   尚未验证的收益承担该双写和一致性风险。
3. **版本和审计链不能断开。** Xiaofei 的自动处理依赖已审核知识、精确的能力计划和
   对应 Eval 证据。外部检索结果必须能回溯到具体来源、Revision、审核状态和运行时
   快照；没有这条映射，就不能成为受控回复依据。
4. **先验证当前闭环更能降低风险。** 当前 Harness 已定义“资料 → KU/CA → Test →
   修正/补充 → 同题复测 → 人工验收 → 启用”的最小闭环。应先取得其可用性、命中、
   纠错和人工验收证据，再判断哪一段确实需要替代或增强。
5. **保持可逆性。** 当前不新增生产依赖、不迁移知识和不改变接口，避免把探索结论变成
   难以回滚的运行时耦合。

## 主线与并行研究

### Harness 主线

继续按现有 P0 交付和验收：Xiaofei 是知识版本、会话状态、所有权、Guardrail、Eval 和
Trace 的唯一权威；LangGraph 和 Mastra 仅在各自的适配器边界承担编排与候选生成。

FLY-140 的冻结资料、模型实验、性能预算、Test CA/Inbox 验收、32 场景评分和最终报告统一
记录在 [`acceptance/fly-140-preview.md`](./acceptance/fly-140-preview.md)。该报告只能判断
Harness P0 目标，不构成 SAG/RAG 同条件直接对照。

主线的结果是后续研究的基线，而不是与研究方案并行写入同一份知识或会话数据。

### 轻量知识治理研究轨道

后续研究必须通过单独的 Multica Issue 和 Feature 启动，且默认满足以下限制：

- 只使用脱敏、隔离的评估数据；不读取或写入 Production、UAT 或现有 Preview 数据。
- 不双写 `ConversationState`、KU/CA、审核状态、Owner/Guardrail 或发送状态。
- 候选方案只能输出可追溯的检索/治理建议；由 Xiaofei 将其映射到已审核的知识版本后
  才能被评估。
- 研究不接入客户发送路径、不改变模型调用授权，也不创建新的长期记忆系统。
- 结果记录能力覆盖、集成边界、失败模式、成本和退出/回滚方式；未达门槛即停止，不把
  试验代码带入主线。

“轻量”不是少做治理，而是限制它只解决被证实的前段缺口，并复用 Xiaofei 既有的租户、
版本、审核、Trace 和授权控制面。

## 评估与采纳门槛

在立项评估前，研究 Issue 必须先冻结一组代表性、脱敏的知识查询和多轮场景，并以当前
Harness 结果作为对照。至少记录以下结果：

| 维度           | 必须证明的结论                                                                                  |
| -------------- | ----------------------------------------------------------------------------------------------- |
| 治理与可追溯性 | 每个候选结果可定位到来源、知识 Revision、适用租户和评估时间；不能绕过审核或发布状态。           |
| 租户与安全     | 无跨租户资料、检索、缓存或记忆泄露；无凭据、Cookie、连接串或客户数据进入测试记录。              |
| 对话与记忆     | Xiaofei 仍是唯一的会话/所有权真相源；重试、回放、失效和人工接管不会产生第二套状态。             |
| 质量与人工成本 | 对照集的检索/引用质量有可复现改善，且不增加人工审核、纠错或故障处理的关键路径负担。             |
| 集成与运维     | 接口、故障降级、可观测性、版本兼容和移除步骤明确；失败时可回退到当前 Harness 而不丢失治理证据。 |

只有同时满足以下条件，才可提出接入方案：

1. 已明确当前 Harness 的具体缺口，并由基线证据证明该缺口影响 P0 后续目标；
2. 研究结果在冻结对照集上有可复现、可审计的收益，而不是仅展示界面或资料导入；
3. 方案不改变 Xiaofei 对租户、KU/CA、会话、Owner、Guardrail 和发送授权的权威；
4. 方案有单独的架构设计、数据生命周期、隔离/删除策略、降级和回滚计划；
5. 人工批准一个新的、独立的 Feature。该批准不是本决策文档或任何 P0 PR 自动授予的。

## 风险与复核时机

当前选择的风险是 Harness 的知识治理能力可能在真实运营中暴露效率或检索质量不足。该
风险由并行研究、可复现评估和明确采纳门槛管理，而不是通过在 P0 期间引入完整外部系统
来掩盖。

在以下任一时机复核本决策：当前 KU/CA 闭环完成可验收测试；代表性知识集显示明确缺口；
或轻量研究满足全部采纳门槛。复核可以决定继续保持 Harness、采用一个受控的轻量适配器，
或另立 Issue 评估更重的 SAG 集成；它不自动改变正在进行的 P0 实现。
